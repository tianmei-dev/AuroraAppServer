# S3.2 契约评审结论 · 设备试用期限不可延长

**状态：方案 A 已确认并完成服务端实施（见 `Task-S3.2-交付说明.md`）。**  
**范围：不修改 Android、不改会员/支付、不改 HMAC 密钥管理。**

---

## 1. 现有实现结论（S3.1）

| 项 | 现状 |
|----|------|
| 接口 | `POST /api/v1/trial/device/activate`，匿名，`X-App-Code` + `{ "deviceKey" }` |
| 身份 | `UNIQUE(app_id, device_key_hash)`，HMAC 不落原始 key |
| 首次 | `trial_started_at = trial_expires_at - 72h = server now` |
| 重复 | 只读已有行，**从不 UPDATE** `trial_expires_at` |
| 并发创建 | `REQUIRES_NEW` + 唯一约束冲突后重查 |
| 限流 | 进程内 IP 桶，与期限无关 |
| 账号 | 试用与登录无关；切换微信不碰 `device_trials` |

**I3.1 根因（与代码一致）：**  
客户端离线先开本地 72h → 首次联网时 Server **尚无记录** → 按联网时刻再发完整 72h。  
这不是“已有记录被延长”，而是 **首次登记偏晚**，相对本地已消耗时间等价于“复活/延长”。  
卸载重装后若 `deviceKey` 不变且 Server 已有行，现逻辑已不会延长；若清数据后本地重置再首连且 Server 无行，仍会发满 72h。

## 2. 能否复用 `trial_expires_at`？

**结论：可以复用，不必新增“有效到期上限”列。**

理由：

1. 产品要的是 **权威到期时刻单调不增（只可提前）**，现字段已是对外返回的到期权威值。  
2. 首次写入与后续缩短都作用在同一列即可：  
   `newExpires = LEAST(existingExpires, serverNow + remainingSecondsCap)`（首次无 existing 时用 `serverNow + min(72h, cap)`）。  
3. 另加 `expires_cap_at` 只会双写同一语义，增加迁移与一致性成本，当前无审计分叉需求。

**不改字段含义的前提（实施时必须写进契约）：**

- `trial_expires_at` = **当前不可突破的到期上限**（只可被压早，不可被推后）。  
- `trial_started_at` / `first_seen_at` = **Server 首次见到该设备试用的时刻**（不因 cap 回拨；不信任客户端绝对首次启动时间）。  
- 旧客户端不传 cap：首次仍 `now+72h`；已有行 **禁止**因缺字段而改到期（只读）。

**因此：需要 Flyway 迁移吗？**

| 方案 | 迁移 |
|------|------|
| **推荐 A：复用 `trial_expires_at` + 条件 UPDATE** | **不需要**表结构迁移；无旧数据强制改写 |
| 备选 B：新增 `trial_expires_ceiling_at` 等 | 需要 V5 + 回填，暂不推荐 |

旧记录“迁移”：无需 SQL 回填。已有 `trial_expires_at` 已是上限；带 cap 的新请求只会 `LEAST` 压早。

## 3. 请求 / 响应字段最终方案（建议）

### 请求

```json
{
  "deviceKey": "...",
  "remainingSecondsCap": 86400
}
```

| 字段 | 必填 | 规则 |
|------|------|------|
| `deviceKey` | 是 | 与 S3.1 相同 |
| `remainingSecondsCap` | **否** | 整数；若出现须 ∈ **[0, 259200]**；缺省 = 旧客户端兼容 |

校验失败：建议 `VALIDATION_FAILED (40004)` 或新增 `TRIAL_CAP_INVALID`（实施时二选一，保持 ApiResponse 风格）。

**禁止：** 客户端传 `trialStartedAt` / `trialExpiresAt` / 绝对首次启动时间（现已忽略多余 JSON 字段，保持）。

### 服务端计算（权威）

令 `now = Clock.instant()`（UTC），`maxDuration = 72h`。

```text
若请求含 remainingSecondsCap：
  candidateExpires = now + Duration.ofSeconds(remainingSecondsCap)

若无记录（首次）：
  expires = 有 cap ? min(now + maxDuration, candidateExpires) : now + maxDuration
  started = first_seen = now
  同一事务内 INSERT（含 expires）

若已有记录：
  无 cap → 不改 expires，直接返回
  有 cap → expires = LEAST(existing.expires, candidateExpires)  （仅当更早才 UPDATE）
  started / first_seen 不变
```

`remainingSeconds` 响应仍为：`max(0, expires - now)`（秒，可截断）。

### 响应

**建议保持现有字段不变**（降低 Android 破坏面）：

```json
{
  "status": "ACTIVE|EXPIRED",
  "trialStartedAt": "...",
  "trialExpiresAt": "...",
  "serverTime": "...",
  "remainingSeconds": 0
}
```

可选增强（非必须，实施前与 Android 确认）：回显 `appliedCap` 或 `expiresTightened: true`，便于联调。  
**证明持久化成功：** HTTP 200 且 `code=0`，且 `trialExpiresAt <= now + remainingSecondsCap`（有 cap 时）；客户端必须以返回的 `trialExpiresAt`/`serverTime` 覆盖本地。

## 4. `trialExpiresAt == trialStartedAt`？

**允许。**

| 场景 | 行为 |
|------|------|
| 首次 `remainingSecondsCap=0` | `started = expires = now` |
| 已有记录被压到 `now` 或更早 | `expires <= now` |

现状态判定：`active = serverTime.isBefore(trialExpiresAt)`。  
相等 → **EXPIRED**，`remainingSeconds=0`。符合“0 秒不可恢复过期”。

库表无 `expires > started` 约束；JPA/API 均应允许相等。  
**Android：** 若本地曾假设 `expires > started`，需改为允许相等/已到期；以 `status`/`remainingSeconds` 为准。

---

## 5. 0 秒到期处理

1. `remainingSecondsCap=0` → `candidateExpires = now`。  
2. 首次：写入 `expires=now`（或实现上 `now`），立即 `EXPIRED`。  
3. 已有未过期：`LEAST` 后到期 ≤ now → `EXPIRED`。  
4. 已过期再报 `259200`：**不得复活**（`LEAST` 保留更早的旧 expires）。  
5. 落库成功后，同 `deviceKey` 任意重试不得恢复为 ACTIVE（除非伪造新 key——既有信任边界，文档已声明）。

---

## 6. 并发与幂等

| 场景 | 方案 |
|------|------|
| 并发首次 INSERT | 保留 S3.1：唯一约束 + 冲突重查 |
| 并发缩短 UPDATE | **原子** `UPDATE ... SET trial_expires_at = LEAST(trial_expires_at, ?) WHERE app_id=? AND device_key_hash=?`；或 `SELECT … FOR UPDATE` 后 min。LEAST 对“取更早”可交换，乱序/并发不会出现更晚值 |
| 幂等 | 相同 cap（含更晚时刻）：候选更晚则 expires 不变；更大 cap：不生效；更小且候选更早：可再压早 |
| 断网重试 | 不新建周期；有行则只读或只压早 |
| 事务 | 首次：INSERT 含最终 expires 单事务；更新：单条条件 UPDATE，禁止“先读后写无锁”丢更新 |

不引入 JVM 内存锁作为正确性依赖。

## 7. 旧客户端兼容

| 客户端 | 行为 |
|--------|------|
| 不传 `remainingSecondsCap` | 首次仍满 72h；已有记录 **绝不因缺字段延长或改写** |
| 新客户端传 cap | 首次按 cap 收紧；已有按 LEAST |
| 仅新客户端升级 | 旧安装首次联网仍可能满 72h（无法获知离线已耗）；**防复活依赖新客户端在首连上报 cap** |

这是产品可接受边界：Server 不能从“绝对首次启动时间”可信推断离线消耗。

---

## 8. 秒级精度与网络时延

- Cap 是客户端发送瞬间的“剩余秒”上界，到达 Server 时墙钟已前进 → 略偏紧可接受，**符合不可延长**。  
- 使用整秒 `Duration.ofSeconds`；`TIMESTAMP(3)` 可保留毫秒，比较用 Instant 即可。  
- **禁止**信任客户端上报的绝对 `firstOpenedAt`。

## 9. Android 需配合修改（本 Task 不改工程，仅列出）

1. 请求增加可选/新版本必填：`remainingSecondsCap = min(本地剩余秒, 259200)`。  
2. 本地已到期或确认用尽时传 `0`。  
3. activate 成功后以 Server `trialExpiresAt`/`serverTime`/`status` 覆盖本地，不得用本地更长窗口覆盖 Server。  
4. 重试使用当前本地剩余（只减不增）；成功响应后禁止再按“完整 72h”重算本地。  
5. 响应校验：允许 `trialExpiresAt == trialStartedAt`；允许首包即 `EXPIRED`。  
6. 账号切换：继续只带同一 `deviceKey`，不传 userId。
